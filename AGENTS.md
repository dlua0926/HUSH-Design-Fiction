# Instructions for AI collaborators

## Start and authority
Read START_HERE.md and STATUS.md first. Inspect latest main and open issues before editing. User instructions in the active session take precedence. WORLD_RULES.md distinguishes user-supported facts, implementation defaults and unapproved ideas; do not flatten these categories.

## Working
- Claim a bounded task in an issue/PR and use a descriptive branch for substantive work.
- Pull/fetch first; never force-push shared history or overwrite teammate work.
- New proposals remain proposals until a human accepts them. Record accepted changes in docs/HISTORY.md and WORLD_RULES.md.
- Keep 20 shared monthly hours,11devices,3daysopeningrenewal,$3.99extra60minutes and historical-data limits coherent unless the user explicitly changes them.
- Do not resurrect automatic family/roommate disclosure as canon. Explain collector, recipient, mechanism and incentive for any new consequence.
- Do not invent user research, tests, teacher quotes, actual product capabilities or completed construction.
- Public repository: do not commit tokens, account details, unreviewed personal photos, raw chats, local absolute paths, or course source PDFs by default.
- Generated concepts are not actual product photos. Distinguish ad renders, physical concepts, UI reference and executable app.

## Progress after each meaningful change
Update STATUS.md and append WORK_LOG.md IN THE SAME COMMIT, with date/timezone, author/agent, files, what changed, validation, blockers and next step. Update asset inventory and AI usage record for new visuals. Preserve earlier log entries. Do not claim deployment or checks without evidence.

## Verification
For code, run appropriate syntax/interaction checks. For visual work, inspect the exported image/PDF. Never claim the existing historic checks verify later edits. Avoid redundant tests for small reversible document edits.

## Synchronisation
GitHub is the shared record, not a realtime multi-agent memory bus. Re-read current files after concurrent changes; use issues/PRs for coordination. Existing Sites deployment is a separate remote, private, and not automatically synced from GitHub. Do not change visibility or deploy publicly without user authorisation.
